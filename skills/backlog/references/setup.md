## Create or configure a tracker

Tracker initialization requires a request to create a backlog or explicit inclusion in an authorized project setup. Installing Ai-Kit, configuring MCP, or finding no tracker is not permission to initialize one. Never rerun `backlog init` over an existing tracker, migrate its storage, or create a second tracker in a child checkout/worktree merely to make discovery work.

1. Resolve the intended workspace/project root and check for an owning tracker using the main skill. A partial `backlog/` directory is not proof of either a working tracker or an empty destination: inspect it and preserve existing data before proceeding. Reuse an existing tracker when it covers the work.
2. Read installed `backlog init --help` and `backlog config --help`. Establish the project name, root, storage mode and scope from the request and existing conventions. Ask only for unresolved ownership or materially different storage/access choices. Do not initialize Git just to enable task tracking.
3. For a new filesystem-only tracker, when the installed CLI supports these flags, use `backlog init '<project name>' --no-git --defaults --agent-instructions none --integration-mode cli` from the approved root. For Git-backed storage, use the approved project policy; inspect init's commit and remote defaults first. Do not copy the filesystem-only example while claiming Git-backed history. Preserve existing instruction files and integrations; do not generate or overwrite them as an incidental setup step.
4. Inspect the resulting effective configuration. Preserve `filesystemOnly`, `remoteOperations`, `autoCommit`, `bypassGitHooks`, signing and access restrictions. Configure workflow through the installed supported mechanism; check help/schema before choosing CLI, MCP or native Web settings/API. Use direct config edits only where native guidance explicitly calls for them. Do not invent a `config set statuses` command or replace task states with labels because a client cannot edit statuses.
5. Establish the project's workflow contract: ordered statuses, initial and final state, entry evidence for each intermediate state, review/acceptance owners, label vocabulary, title/description language, native types/priorities and blocker representation. Reuse the canonical policy location. If absent, create one concise product workflow document through native Backlog document commands after reading their help; do not duplicate a kit skill or installation manual into the tracker. Link the policy from relevant task artifacts.
6. Read configuration back and verify the actual board/list with the owning root. With MCP, verify its resolved tracker; with Web, verify the project path, not just its display name. Confirm initial/final status, configured intermediate states, and safety settings. Use a disposable tracker for sample tasks rather than creating fake work in the real backlog. Report the root, storage, workflow, policy reference and any unverified integration.

### Choosing a workflow

Keep existing project status names unless the owner requests a change. When creating a workflow, use the fewest states that distinguish real queues, handoffs or acceptance gates. A development workflow may use `To Do -> In Progress -> Review -> On Dev -> Ready for Release -> Done`; these names are a proposal, not global defaults. Define the evidence using the execution contract before relying on them. `On Dev` means actually deployed to the development environment, not merely ready to deploy. A separate `Ready for Testing` state is useful only when the project needs a distinct testing queue. Research, documentation and infrastructure work need their own applicable delivery gates, not fictional dev deployments.

When changing an existing status list, inspect tasks using affected states and agree any mapping before removing or renaming them. Preserve IDs, history and unrelated metadata. Adding columns does not justify moving existing tasks. Keep the final status last where native tooling treats the last configured state as completed. A policy change does not itself grant merge, deploy or production access.
